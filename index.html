Clase 2· Unidad 01

Calidad del software y UML

Un sistema no es bueno solo porque funciona: debe ser mantenible, escalable, disponible y rápido. Y para diseñarlo se usan los planos del software: los diagramas UML.

En simple

La calidad funcional responde: "¿el programa hace lo que debe?". La calidad arquitectónica responde: "¿el programa se comporta bien en el mundo real?" — con muchos usuarios, muchos cambios y poco presupuesto.

Atributos de calidad (no funcionales)

ISO/IEC 25010

Mantenibilidad

Qué tan fácil es modificar el sistema. Un sistema mantenible tiene alta cohesión y bajo acoplamiento.

Señal: cambiar una regla no rompe lo demás.
ISO/IEC 25010

Escalabilidad

Manejar más trabajo añadiendo recursos: más máquinas (horizontal) o más hardware en una sola (vertical).

Señal: más tráfico, mismo rendimiento.
ISO/IEC 25010

Disponibilidad

Porcentaje de tiempo que el sistema está operativo. "Cinco nueves" (99.999%) son apenas 5 minutos de caída al año.

Señal: réplicas y failover automático.
ISO/IEC 25010

Rendimiento

Latencia (tiempo por petición) y throughput (peticiones por segundo) bajo carga normal o pico.

Señal: 45 ms de respuesta, no 2 s.

Conceptos base

Concepto

Abstracción

Ocultar los detalles complejos tras una interfaz simple: interesa qué hace, no cómo.

Concepto

Encapsulamiento

Agrupar datos y comportamiento en una clase, restringiendo el acceso directo a sus campos.

Concepto

Cohesión y acoplamiento

Queremos alta cohesión (cada clase hace una cosa) y bajo acoplamiento (las clases dependen poco entre sí).

UML y diagramas

Estructural

Diagrama de Clases

Clases, atributos, métodos y sus relaciones.

Estructural

Diagrama de Componentes

Organización lógica en paquetes reutilizables.

Estructural

Diagrama de Despliegue

Topología física: servidores, contenedores y la red.

Comportamiento

Casos de Uso

Qué puede hacer cada actor. Ej: Estudiante → Consultar calificaciones.

Comportamiento

Diagrama de Secuencia

Mensajes entre objetos ordenados en el tiempo.

Relación

Asociación

Conexión estructural simple entre clases (un Profesor dicta un Curso).

Relación

Agregación · rombo vacío

Relación "todo-parte" débil: la parte existe sin el todo.

Relación

Composición · rombo relleno

Relación "todo-parte" fuerte: si muere el todo, muere la parte.

En simple

Agregación = "una universidad tiene profesores" (el profesor sigue sin la universidad). Composición = "un libro tiene páginas" (sin libro no hay páginas).

Casos de uso

«include» — obligatorio

El caso base siempre ejecuta al otro. Consultar calificaciones siempre requiere Iniciar sesión.

Casos de uso

«extend» — opcional

El caso base puede incluir al otro de forma condicional. Cargar notas puede extender con Modificar nota.

Clase 3· Unidad 02

Persistencia y acceso a datos

La persistencia hace que los datos sobrevivan al reinicio. La pregunta es cómo guardarlos sin amarrar el negocio a una base de datos específica.

En simple

Persistencia = datos que sobreviven al reinicio. Si solo viven en la memoria RAM, se pierden al apagar el programa. Las bases de datos relacionales los guardan en tablas garantizando integridad con ACID.

Conceptos esenciales

RDBMS

Relacionales

Tablas + ACID (Atomicidad, Consistencia, Aislamiento, Durabilidad). PostgreSQL, MySQL.

NoSQL

Documentales / KV

Gran volumen no estructurado o de rápido crecimiento. MongoDB, Redis.

Modelo

Entidad-Relación

Clave primaria (PK) identifica; clave foránea (FK) relaciona (1:N).

Estrategia

Connection Pooling

Abrir conexiones es caro: se reutilizan conexiones ya abiertas (HikariCP).

Estrategia

Réplicas

Maestro escribe, esclavos leen. Escala las lecturas pesadas.

Repository = el mozo del restaurante. Tu lógica pide "dame el usuario con id 7" sin saber si viene de PostgreSQL o MySQL. Si cambias de base de datos, solo cambia el mozo.

ORM, JPA y Hibernate

Problema

Desfase de impedancia

Los objetos (clases, herencia) no encajan con las tablas (columnas, FKs). El ORM es el puente.

Estándar

JPA

Define el contrato: anotaciones @Entity, @Id, @Table. No hace el trabajo real.

Motor

Hibernate

Lee las anotaciones JPA y genera el SQL nativo. Es el proveedor más popular.

Usuario.java · entidad JPA mapeada a la tabla "usuarios"
@Entity
@Table(name = "usuarios")
public class Usuario {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String email;
}

Clase 4· Unidad 03

Errores, resiliencia y seguridad

El software profesional asume que las cosas van a fallar y que alguien querrá atacarlo. Se diseña para caer con elegancia, registrarlo todo y proteger el acceso.

Errores y logging

Excepciones

Checked

Fallos recuperables externos. El compilador obliga a capturarlas.

Excepciones

Unchecked

Errores de lógica interna. Ocurren en ejecución sin captura forzada.

Logging

Niveles de log

DEBUG → INFO → WARN → ERROR. El diario de vida de la app.

Buenas prácticas: centralizar errores con manejadores globales (por ejemplo @ControllerAdvice en Spring Boot) en vez de plagar el código de try-catch.

Tolerancia a fallos

Patrón

Circuit Breaker

Como un disyuntor: si el servicio falla mucho, bloquea el tráfico para no colapsar al cliente.

Patrón

Retry

Reintenta peticiones fallidas asumiendo que el error es temporal.

Patrón

Fallback

Respuesta degradada pero útil (ej: caché) en lugar de un error.

Autenticación, autorización y JWT

Identidad

Autenticación · ¿Quién eres?

Validar credenciales y emitir un token firmado.

Permisos

Autorización · ¿Qué puedes hacer?

Leer el token y comprobar el rol (ROLE_ADMIN).

JWT · Parte 1

Header

Algoritmo y tipo de token. Ej: {"alg":"HS256","typ":"JWT"}.

JWT · Parte 2

Payload

Los "claims": datos del usuario y roles. Ej: {"sub":"123","roles":["ROLE_ADMIN"]}.

JWT · Parte 3

Firma

Valida que nadie alteró el token. Si cambias un carácter, la firma no coincide y el servidor lo rechaza.

OWASP Top 10

A01

Control de acceso roto

Acceder a datos ajenos cambiando un id en la URL. Mitigar: validar en servidor que el sub del JWT sea el dueño.

A02

Fallos criptográficos

Datos sensibles sin cifrar o con algoritmos débiles.

A03

Inyección

SQLi / XSS: código malicioso dentro de entradas del usuario.

A04

Diseño inseguro

Falta de controles de seguridad desde el diseño.

Clases 5 y 6.3· Unidad 04

Estilos arquitectónicos

El estilo es la topología global del sistema. El patrón es la solución táctica de un componente. Un estilo puede usar muchos patrones.

En simple

Estilo = "el sistema es un edificio de apartamentos" (macro). Patrón = "dentro de cada apartamento, los muebles van así" (micro).

Estilo

Monolito

Todo en una sola unidad desplegable (.jar / .war). Ideal para arrancar.

Pro: simple, un solo deploy. Contra: punto único de fallo, escala todo o nada.
Estilo

Monolito modular

Un solo ejecutable con módulos lógicos estrictos.

Pro: despliegue simple + orden. Contra: escalado global.
Estilo

Cliente-servidor

Clientes piden recursos y un servidor central atiende por red (HTTP/REST).

Pro: clásico. Contra: servidor central = cuello de botella.
Estilo

Microservicios

Cada capacidad de negocio es un proceso independiente que habla por red.

Pro: escala por servicio, aisla fallos. Contra: complejidad y latencia.
Estilo

SOA

Servicios integrados por un Bus central (ESB) con SOAP/XML.

Pro: integra sistemas heredados. Contra: ESB = punto de fallo.
Estilo

Serverless (FaaS)

Funciones efímeras lanzadas por eventos; la nube escala sola.

Pro: escala automática. Contra: cold starts.
Estilo

Event-driven

Componentes emiten y consumen eventos asíncronos por colas (Kafka, RabbitMQ).

Pro: desacoplamiento total. Contra: difícil de depurar.
Estilo

Peer-to-peer

Red descentralizada: cada nodo es cliente y servidor a la vez.

Pro: sin servidor central. Contra: complejidad muy alta.

Clases 6 y 6.1· Unidad 05

Patrones arquitectónicos

Soluciones probadas y repetibles para organizar el código. Nacieron para acabar con el código espagueti.

Patrón

En capas

Presentación → Negocio → Datos.

Cuándo: sistemas tradicionales.
Patrón

Clean

Reglas de negocio al centro, frameworks afuera.

Cuándo: sistemas empresariales.
Patrón

Hexagonal

Puertos y adaptadores. El negocio no conoce la tecnología.

Cuándo: APIs y sistemas que cambian de tecnología.
Patrón

Onion

Dominio en el núcleo, dependencias hacia dentro.

Cuándo: apps basadas en dominio.
Patrón

MVC

Modelo (datos) / Vista (UI) / Controlador (entrada).

Cuándo: CRUD rápido.
Patrón

CQRS

Lecturas (queries) separadas de escrituras (commands).

Cuándo: mucha lectura vs escritura.
Patrón

Event-driven

Comunicación asíncrona por eventos y colas.

Cuándo: microservicios desacoplados.
Patrón

Microkernel

Core mínimo + plugins (IDEs, editores).

Cuándo: apps extensibles.

Arquitectura Hexagonal (Ports & Adapters)

De Alistair Cockburn (2005). El dominio es el centro; la tecnología se conecta por puertos (interfaces) y adaptadores (implementaciones).

Núcleo

Dominio

Entidades y reglas de negocio en lenguaje puro, sin imports de Spring/JPA.

Contrato

Puertos

Interfaces de entrada (lo que ofrece) y salida (lo que necesita, ej: guardar).

Implementación

Adaptadores

REST Controller y JPA Repository traducen el mundo externo al dominio.

Regla de oro: las dependencias fluyen siempre hacia el centro. Adaptadores → Puertos → Dominio.
Libro.java · dominio puro, sin anotaciones de infraestructura
package domain.model;

public class Libro {
    private Long id;
    private String titulo;
    private boolean disponible;

    public void prestar() {
        if (!disponible) {
            throw new IllegalStateException("El libro no está disponible");
        }
        disponible = false;
    }
}
PrestarLibroUseCase.java · depende de la interfaz, no de PostgreSQL
public class PrestarLibroUseCase {
    private final LibroRepository libroRepository;

    public PrestarLibroUseCase(LibroRepository repo) {
        this.libroRepository = repo;
    }

    public void ejecutar(Long libroId) {
        Libro libro = libroRepository.buscarPorId(libroId);
        libro.prestar();               // lógica de negocio
        libroRepository.guardar(libro); // la infraestructura la implementa el adaptador
    }
}
En simple

Hexagonal = el negocio no sabe de "plomería". Cambiar de Spring a Quarkus o de PostgreSQL a MongoDB solo toca los adaptadores, nunca el dominio.

Frameworks y herramientas

Un framework da estructura, ORM y servidor HTTP listos. La clave es elegir con criterio, no por moda.

Tipos

Opinados

Imponen estructura de carpetas e inyección de dependencias: Spring Boot, NestJS, Laravel.

Tipos

No opinados (micro)

Libertad total, tú creas la estructura: Express, Flask, Gin.

Single Page App

Un HTML + JS que renderiza todo en el navegador. Fluido, pero penaliza el SEO.

Librería

Mobile

Flutter vs React Native

Flutter dibuja en canvas propio; React Native usa vistas nativas mapeadas.

Persistencia

ORM / ODM / SQL Mapper

ORM abstrae el SQL (Hibernate, Prisma). ODM mapea documentos NoSQL (Mongoose). SQL Mapper deja el SQL en tus manos (MyBatis).

Patrones: Active Record (el objeto se guarda solo, Django) vs Data Mapper (un repositorio guarda, Hibernate).
Calidad

Testing · la pirámide

Unitarias (JUnit, Jest) — base grande y rápida. Integración (Mockito). E2E (Playwright, Cypress) — pocas y caras.

Regla: muchas unitarias, pocas E2E.
Operaciones

DevOps

Contenedores: Docker. Orquestación: Kubernetes. CI/CD: GitHub Actions. IaC: Terraform. Config: Ansible.

GitOps (ArgoCD): el repo Git es la fuente de verdad del clúster.
Seguridad

Auth moderna

OAuth2 = autorización (scopes). OpenID Connect = autenticación (ID tokens). Keycloak = IAM central con SSO.

Spring Security filtra con hasRole('ADMIN').

Clase 7· Unidad 07

Diseño, SOLID y calidad

La arquitectura son las decisiones globales difíciles de cambiar. El diseño es el detalle interno de cada módulo.

Nivel

Alto nivel (HLD)

Estructura general: módulos, base de datos, APIs. Entregables: diagramas C4, diagramas de red.

Nivel

Bajo nivel (LLD)

Detalle técnico: clases, métodos, patrones. Entregables: diagramas de clase UML.

Los 5 principios SOLID

S

Responsabilidad Única

Una sola razón para cambiar

Cada clase debe tener una sola razón para cambiar. Una clase no debe guardar en BD, mandar emails y cobrar pagos a la vez.

// UsuarioService hacía todo // UsuarioRepository, NotificadorEmail, ...
O

Abierto / Cerrado

Extender sin modificar

Abierto a extensión, cerrado a modificación: añadir funciones sin tocar el código existente (polimorfismo).

// ReportePDF y ReporteExcel extienden // ReporteFormato sin modificar el generador
L

Sustitución de Liskov

Las subclases no rompen

Las subclases deben poder reemplazar a su clase base sin romper el sistema.

// un Avestruz que "vuela" y lanza // excepción rompe el polimorfismo
I

Segregación de Interfaces

Interfaces pequeñas

Los clientes no deben depender de interfaces que no usan.

// Impresora no debería implementar // enviarFax() de una interfaz "gorda"
D

Inversión de Dependencias

Depender de abstracciones

Los módulos de alto nivel no dependen de los de bajo nivel; ambos dependen de abstracciones.

// GestorPedido depende de interface // Database, no de MySQLConnection
!

Heurísticas

DRY · KISS · YAGNI

DRY: no repitas lógica. KISS: mantén lo simple. YAGNI: no programes lo que "quizá" hará falta. Y programa a interfaces, no a implementaciones.

// YAGNI: 3 interfaces + factory para una // pasarela que el cliente nunca cambiará

Antipatrón: God Object

Una clase de 12,000 líneas que hace SQL, emails y pagos. Viola SRP; se refactoriza separando responsabilidades.

Antipatrones a evitar

Big Ball of Mud (sin arquitectura), Spaghetti (todo enredado), Golden Hammer (una herramienta para todo), Lava Flow (código muerto), Copy & Paste (bugs replicados).

En simple

Todo diseño es una balanza (trade-off): más seguridad cuesta rendimiento, más redundancia cuesta dinero, más interfaces cuesta simplicidad. El arquitecto elige el equilibrio según el negocio.

i Casos reales: lo que hicieron las empresas▼
  • Netflix — microservicios + Chaos Monkey: tiran servidores a propósito para probar resiliencia.
  • Amazon — de monolito a microservicios con base de datos por servicio.
  • Spotify — micro-frontends por squads (playlists, search, player).
  • Bancos — consistencia ACID y cifrado no negociables.
  • Moodle — LAMP monolítica escalada con réplicas de lectura + Nginx.

Proyecto· ViajeCheck

ViajeCheck: la teoría en un proyecto real

Sistema web para agencias de viajes. Un backend en .NET 8 con Clean Architecture y CQRS, y un frontend en Angular 16. Aquí se ven aplicados los conceptos de la materia.

En simple

ViajeCheck no inventa nada nuevo: es la teoría del curso puesta a trabajar. En cada capa y en cada archivo aparece un concepto que ya estudiamos — arquitectura limpia, CQRS, SOLID, Repository, JWT, testing y DevOps.

La arquitectura en la práctica

El backend replica casi exactamente la arquitectura hexagonal/clean de la Unidad 05. Cada carpeta del proyecto es una capa.

CQRS en código: un command y su handler

Así se ve el flujo de escritura del login. El controller delega en MediatR; el handler es la única pieza que conoce la lógica.

LoginCommand.cs · un comando (escribir / autenticar)
public class LoginCommand : IRequest<string>
{
    public string Email { get; set; }
    public string Password { get; set; }
}

public class LoginHandler : IRequestHandler<LoginCommand, string>
{
    private readonly IAuthService _authService;

    public LoginHandler(IAuthService authService) => _authService = authService;

    public async Task<string> Handle(LoginCommand request, CancellationToken ct)
    {
        var token = await _authService.LoginAsync(request.Email, request.Password);

        if (string.IsNullOrEmpty(token))
            throw new InvalidCredentialsException();  // → ExceptionMiddleware

        return token;
    }
}

Seguridad: el frontend protege las rutas

Angular · guard

AuthGuard

Si no hay sesión, redirige a /auth/login. Protege las rutas del panel.

Angular · interceptor

AuthInterceptor

Agrega Authorization: Bearer {token} a cada petición HTTP automáticamente.

auth.interceptor.ts · JWT en cada petición (clase 4)
intercept(req: HttpRequest<any>, next: HttpHandler) {
  const token = this.authService.getToken();
  if (token) {
    req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  }
  return next.handle(req);
}

Recorrido completo de una petición: Angular (AuthInterceptor agrega el JWT) → Controller de la WebAPI → MediatR envía el Command → Handler (Application) → Repositorio (Infrastructure) → Base de datos. Si algo falla, el ExceptionMiddleware devuelve un JSON limpio en vez de un crash.
